# 聊天记录入库

[`SKILL.md`](SKILL.md) 的 ① 收 推下来的参考。**只在要导入微信 / 飞书聊天记录时读。**

**这一份解决的是整个 skill 最脏的一段活**：需求方的需求散在几万条闲聊里，没有一条写着「这是个需求」。

---

## 铁律：导出件只读，不改，不删

**导出的原文件放在 `raw/_src/`，一个字都不许改。** 筛出来的东西写成**派生文件**，派生文件里**每条都指回原文件的位置**。

**为什么**：三个月后两个人对同一句话的理解分岔时，**唯一能仲裁的就是原始那条消息**。派生件被改过，仲裁就没用了。

```
.intent/raw/
  _src/                                ← 导出件原样放这，只读
    wechat-<群名>-20260901-20261003.txt
    feishu-<群名>-20260901-20261003.md
  20-chat-wechat-20261003.md           ← 派生：筛出来的，带出处
  21-chat-feishu-20261003.md           ← 派生：筛出来的，带出处
```

**整棵树的唯一真相源在 [`SKILL.md`](SKILL.md) 的「入口」一节** —— 这里只画聊天这一支。

## 导出工具（社区工具，非官方）

**这两个平台都没有官方的一键全量导出。** 下面这些是社区工具，**用之前先确认它们在你的机器上能跑、且你愿意让它读你的聊天数据库**。

**微信这一侧的路正在关**：至少 [chatlog](https://github.com/sjzar/chatlog) 是收到**微信官方函件**后删掉全部代码与提交历史的（2025-10-20）；留痕 / WeChatMsg 也清空了源码，官网 `memotrace.cn` 已经打不开。**这不是「工具停更」，是这条路有合规风险** —— 要不要走，由需求方自己判断。

| 平台 | 工具 | 导出的形态 | 注意 |
|---|---|---|---|
| 微信 | [WeChatMsg / 留痕](https://github.com/LC044/WeChatMsg) | HTML / Word / **CSV / TXT**，可按时间段和联系人导 | **已失效**：仓库只剩 `doc/` 和 readme，官网没了，也没有 release。作者写明不再更新 |
| 微信 | [shixiaogaoya/MemoTrace](https://github.com/shixiaogaoya/MemoTrace) | 同上 | **不是另一实现，是上面那个项目的第三方 fork** —— 上游清空后它仍留着完整源码（含微信 4.0）。要读源码只能看它，但它是别人拷的，不是作者发布的 |
| 微信 | [wechat-mac-export](https://github.com/rmqg/wechat-mac-export) | 文本 | macOS。上面几家里**唯一还在动的**（2026-09 仍有提交），风险与同源项目一样 |
| 飞书 | **消息导出到文档**（官方功能） | 飞书文档 | [官方说明](https://www.feishu.cn/hc/zh-CN/articles/158045525235-%E4%BD%BF%E7%94%A8%E6%B6%88%E6%81%AF%E5%AF%BC%E5%87%BA%E5%88%B0%E6%96%87%E6%A1%A3%E5%8A%9F%E8%83%BD)。需飞书 V7.20+；**话题群、保密模式、禁止转发的消息导不出来** |
| 飞书 | [feishu-message-for-llm](https://github.com/so2liu/feishu-message-for-llm) | **转成 LLM 易读的 Markdown** | 走飞书开放接口，需配应用权限。个人项目、无 license、几乎没人用 —— 先自己过一遍代码 |
| 飞书 | [飞书开放接口 IM v1](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list) | JSON | 拉消息正文走「获取会话历史消息」；要从接口拉，得自己写脚本 |

> 本表最后一次核对日期：2026-10-12（三个月后一眼判断它过没过期 —— **这张表烂得比 skill 其余部分快**）

**导不出来时的退路**：飞书让人用官方「消息导出到文档」，把文档**复制粘贴**成 txt/md 落盘；微信没有官方导出、社区工具又在下架，就让他**按时间段自己复制粘贴，或截图**走 `/to-questionnaire`。**不要让他手打** —— 手打会顺手润色，原话就丢了。

**导出前先定范围**：**按时间段 + 按联系人或群**。全量导出会得到几万条无关消息，筛选成本远超收益。范围由需求方定（他知道哪段时间在聊这件事）。

## 三种形态，怎么读

| 形态 | 长什么样 | 怎么切 |
|---|---|---|
| **A · 一行一条（CSV / TXT）** | `<时间>,<发送人>,<内容>` | 一行一条最省事；**内容里有换行时会在下一行继续** —— 看下一行开头有没有时间戳，没有就是上一条的续行，**必须合并回去** |
| **B · 连续文本（微信导出的 TXT）** | 发送人和时间各占一行，内容在下面 | 以**时间戳行**为切分点；时间戳行前一行是发送人 |
| **C · Markdown / 文档（飞书）** | 发送人 + 时间 + 正文，可能带引用和话题 | 以**发送人块**为切分点；**引用回复要跟原消息对上**，否则会读成独立的一句 |

**形态判断不清时，先读 200 行再说。** 猜错了切分点，整份记录会错位，而错位的记录看起来是正常的 —— **这是这一站最贵的错误**。

**切完之后抽查三处**（文件头、文件中、文件尾）：随便挑一条，**回原文件核对发送人和时间**。三处都对得上，才继续。

## 筛选：从闲聊里挑出需求

**这是最难的一步，也是最不能用关键词做的一步。**

**为什么不能用关键词**：需求恰恰**不会**用「需求」这个词说出来。说得出口「这是个需求」的人，本来就会写文档，也就不用这个 skill 了。

**判据只有一条**：**这条消息里，有没有一件「系统可以做的事」？**

### 五种真需求句式

| 句式 | 例子 | 它其实是 |
|---|---|---|
| **愿望句** | 「要是能……就好了」「最好能……」 | 功能需求 |
| **痛点否定句** | 「这个不能……」「每次都要……」 | 功能需求（反向说的） |
| **疑问句** | 「你们那个 X 能不能……？」 | 功能需求（他在试探可行性） |
| **现状描述句** | 「我们现在是这么弄的：先……再……」 | **自动化机会**（他没说要自动化，但他描述了一个可自动化的流程） |
| **抱怨句** | 「太麻烦了」「老是忘」「又搞错了」 | **最真实的需求源** |

**「现状描述」和「抱怨」是两份最容易漏的矿。** 前面三种他自己知道那是个需求；后面两种他不知道 —— **他知道的只是「这样很烦」，而「这样很烦」翻译过来就是需求。**

### 明确不是需求的

寒暄、约时间、转发文章且**无评论**、纯表情、纯图片且**无配文**、别人说的话（**只收需求方本人说的**，除非第三方转述的是需求方的话）。

### 收的时候一并不许做的两件事

- **不许改写** —— 错别字、口语、方言词全部保留，另起一栏写你的理解
- **不许合并** —— 他用不同的话说了三遍同一件事，**收三条**，在派生件里做关联。**合并是 ③ 译 的活**，不是这一站的活

## 派生件格式

**一段一条，逐字，带出处。** 模板见 [`templates/raw-chat.md`](templates/raw-chat.md)。骨架：

```markdown
## C-014
**原话**：「要是能直接看出来谁做得好就好了」
**出处**：`_src/wechat-XXX-20260901-20261003.txt` L4821
**时间**：2026-09-12 15:04
**发送人**：<需求方>
**我的理解**：<产品语言的初译，允许不准>
**关联**：C-009（同一件事，9-08 说过一次）
**状态**：未译
```

**段落编 `C-NNN`，全局唯一，不按文件重新编号。** 需求条目（③ 译 的 `R-NN`）的「原话」栏就引这个编号 —— **这是原话到产品之间那根线。**

**「关联」栏必须在收的时候填。** 同一个人说同一件事说三遍，中间那句往往是最清楚的 —— **筛的时候不标关联，③ 译 的时候就得重读一遍全量记录。**

## 语音、图片、文件、撤回

**这四类在导出件里通常只剩一个占位标记，而它们经常正是需求本身。**

| 类型 | 导出后剩什么 | 怎么办 |
|---|---|---|
| **图片** | `[图片]` | **图片常常就是需求**（表格照片、手写流程图、别人的界面截图）。**只有人能看图** → 走 `/to-questionnaire` 让他描述，或让他**把图单独发给你** |
| **语音** | `[语音]` | 只有人能听 → 同上。**语音内容由人转述，agent 不猜** |
| **文件** | 文件名 | 文件名往往够用（「团体活动记录表.xlsx」本身就说明了需求）。要内容 → 让他发文件 |
| **撤回** | 通常消失 | 撤回的那条常常是最真实的抱怨。**发现某条对话上下文接不上时，直接问一句「你撤回的那条是什么」** |

**这一类残留在派生件里逐条建行**：位置、类型、上下文各一句、**缺的是什么**，编 `M-NN` 号。**读到不就读不到，也照样登记** —— 不登记，「这里曾经有个需求」这个事实就一起没了。

**`/wizard` 的用法**：如果同一类材料（比如一批照片）要人反复导出、拍照、转文字，**用 `/wizard` 生成一个交互脚本**，把「打开哪、拍什么、存哪」固化下来，别每次口头交代一遍。

## 收口判据

**三条全中，① 收 才算完**：

1. **每份原料都有落盘文件**，且**每一条都有出处**（文件名 + 行号，或时间戳 + 发送人）—— **硬性对账**：派生文件末尾必须保留「抽检核验表」，实查填入 5 条消息的出处位置与前 20 字，5 条全部吻合
2. **图片 / 语音 / 文件 / 撤回这四类残留全部登记了** —— 一条不漏，且写明缺什么
3. **数出三个数字**：原话条目数 · 话题数 · 还没定的话题数。**逐条数出来的，不是估的**

**第 1 条的抽检核验表格式（派生件末尾必填交付物）**：

| 抽检ID | 导出文件出处（行号/时间戳） | 发送人 | 原始消息前20字摘录 | 核验状态 |
|---|---|---|---|---|
| C-002 | L104 (14:20) | 张三 | 「...」 | ✅ 一致 |
| C-008 | L512 (15:01) | 李四 | 「...」 | ✅ 一致 |
| C-014 | L1280 (09:12) | 张三 | 「...」 | ✅ 一致 |
| C-025 | L2104 (11:30) | 王五 | 「...」 | ✅ 一致 |
| C-033 | L3400 (16:45) | 张三 | 「...」 | ✅ 一致 |

（少于 5 条或未落盘核验表，本阶段视为未完工，不准推进至 ② 判）

**漏一条的代价**：**漏掉的那条不会被发现** —— 因为没有任何东西可以拿来对照。这正是「需求总是不明确」的机械原因。

## 一段示例（虚构，只看格式）

```markdown
## C-014
**原话**：「每次带完还得手写一遍，写完自己都懒得看」
**出处**：`_src/wechat-团体组-202609.txt` L4821
**时间**：2026-09-12 15:04
**发送人**：<需求方>
**我的理解**：带完活动后的记录环节太费力 → 需要降低记录成本（不是「需要报表」）
**关联**：C-009（9-08「记录太麻烦」）、C-021（9-20「能不能手机上直接点」）
**状态**：未译
```

> 注意「我的理解」一栏**故意写成初译且允许不准** —— 它的作用是给 ③ 译 一个起点，不是定论。**把初译写成定论，就等于在这一站已经替需求方拍板了。**
