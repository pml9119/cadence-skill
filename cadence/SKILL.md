# Cadence

**Scrumban 式的项目调度层。** 它同时扮演两个角色：**产品经理**（做什么、先做哪个）和 **项目经理**（几个在做、卡在哪、什么时候算完）。

它架在 matt pocock 的工程 skills 之上：那些 skills 说每一步**怎么做**（采访、spec、票、实现、评审），cadence 说**做什么、什么时候做、同时做几个**。**分两层**：先用「方向层」决定做什么，再用「流动层」安排怎么流动。

**它把变动当常态收下** —— 模糊的进「迷雾」，改动的走变更（新建 / 换范围 / 作废都算），**在制品不受打扰**。

**Scrumban 借来的三件**：**看板**（六列，票不跳列）· **在制品上限**（N）· **拉动**（「待开工」少于阈值才从「发现」拉票）。
**去掉了**：时间盒、承诺、故事点、速度。**加上去的**：三类 cadence 事件 —— 每日看一个数、每周回顾、触发式补充。

**它假设一个人**同时管方向又管进度 —— 这里的"团队"就是你和 N 个 agent。**它挡的失败是「没人读过的代码山」。**

**同一条规矩在本文件里只写一遍** —— 重述会让两处各自漂移。**别让同一条规矩住进两个文件** —— 要改时你会漏掉一处。

**你只读 `SKILL.md` 就能跑完全程。** 五个参考文件**按分支读**，不必通读 —— **分支表在文末「参考」**，这里不重述。

## 入口：先盘一次，再收

**两个入口，名字就是它的动作**（避开编号 —— **六列已经占用了 0–5**）：

| 入口 | 干什么 | 什么时候跑 |
|---|---|---|
| **盘点**（`inventory`） | 搞清楚**手上有什么**：功能全清单 + 入口总表 | **第一次接手项目必跑**；之后每个里程碑过闸、每周复盘时**重跑**（盘点有保鲜期） |
| **收原话**（`raw`） | 搞清楚**对方要什么**：收原话 → 判 → 译 | **之后每一轮** —— 大部分时间在这里 |

**盘点是一道入口闸门。** 没盘过、或上次盘点已过期（超过一个里程碑，或超过一周，先到者为准）→ **不许往下走任何一步**。

**手上什么都没有的项目，盘点照样跑** —— 产出会是「已有功能 0 条」。**这个 0 是数出来的、落了盘的**，不是假设的；后面「里程碑待定」才站得住脚。

**收原话不能替盘点** —— 收得再全也只是「对方要什么」。不知道「手上有什么」，就没有东西可以拿来对照，**漏掉的需求没人能发现**。

**落盘：一份 `.intent/` 装全部** —— 两个入口的产出都在里面，**跟代码一起进版本库**：

```
.intent/
  inventory/            ← 盘点：入口总表 · 功能全清单 · 分块明细
  raw/                  ← 收原话：逐字，只读
    _src/               ←   原文整份原样放这，只读（导出件 / 那份文档）
    10-doc-*.md         ←   文档切出来的
    20-chat-*.md        ←   聊天记录筛出来的
    30-interview-*.md   ←   当面说的、这轮对话说的
  drift.md              ← 两边共用（见下）
  GLOSSARY.md           ← 他的词 → 产品词。③ 译 全靠它
  requirements.md       ← 需求条目（③ 写）
```

**这棵树是唯一真相源。** 骨架在 [`templates/`](templates/)。

**`drift.md` 只有一份** —— 盘点的「与旧自述冲突」和收原话的「文档说 A、原话是 B」**是同一件事**，都写这一份，**别各写一份**。

**两条边界别混**：

- **决策账本不在 `.intent/` 里** —— 它只认**一处**，位置由 `docs/agents/flow.md` 指明（通常是 `/setup-cadence` 交付的仓库根 `DECISIONS.md`）。产生的决策**追加进那一份**，不新建第二份
- **`.intent/` 装原料，`docs/agents/direction.md` 装配置** —— 前者是盘点结果、原话与需求条目；后者是优先级 / 里程碑 / 依赖表。**两者不是一回事，别互相代替**

## 全链路

**①—④ 是「进来之前」的四站**（收原话 → 判 → 译 → 放行）；**⑤ 就是方向层的 D1/D2**（排优先级、定里程碑）—— 它不重复出现，两个名字指同一件事：

```
盘点 ── 只跑一次（之后按里程碑/每周重跑）
     盘出：入口总表 · 功能全清单 · 漂移清单  →  .intent/inventory/

                    ↓ 盘完之后

① 收原话 ─⇥ 换 context ⇥─→ ② 判 三类判断 ──→ ③ 译 产品语言 ──→ ④ 放行 闸 S → 闸 T
   ├─ 原文只读                    ├─ 需求条目带原话锚点        （人过闸）
   ├─ 逐条标可信度                └─ 批不过 5 条
   └─ 收口数数（数哪几个，按原料）
                    ↺ 之后的每一轮都在 ①②③ 里循环

                              ↓ 带原话锚点的需求条目

方向层 ── 决定做什么
   ⑤ 排：优先级（D1） → 里程碑（D2）      ← ⑤ 和 D1/D2 是同一件事
   需求：模糊进迷雾 · 改动走变更（在制品不动）
                              │
          ═══ 交界 ═══ 交出一张排好序的候选清单
                              │
流动层 ── 决定怎么流动
   0 迷雾 → 1 发现 ─闸 S→闸 T→ 2 待开工 → 3 进行中 → 4 待验收 ─闸 V→ 5 已完成
                                         在制品 ≤ N           （你裁决）
```

> 上半段的 ①②③④ 是「进来之前」的四站，下半段的 0–5 是**看板六列**（进来之后）。**两套编号互不相干。** 两个入口另有名字（**盘点** / **收原话**），**不占数字**。

**盘点**只跑一次（**第一次必跑**）；**收原话**之后每轮都跑。
**决定做什么**读 D1；**安排怎么流动**读流动层；**出汇报**读 D3。
**① 收 和 ② 判之间换 context** —— 收完就交回（`/handoff`），别在同一个 context 里接着译。

## 两层，职责分开

| 层 | 回答 | 落盘在 | 边界 |
|---|---|---|---|
| **方向层** | 先做哪个 · 到哪算到 · 怎么讲给人听 | `docs/agents/direction.md` | 写代码和 spec 归工程 skills；票的列间流转归流动层（方向层只给票打「待批准」标记） |
| **流动层** | 同时跑多少 · 卡在哪 · 谁验收 · 什么时候复盘 | `docs/agents/flow.md` | 排优先级、定里程碑归方向层 |

**盘点（`inventory`）和收原话（`raw`）跨在两层之间**：盘点盘的是**存量**，收原话译的是**需求** —— 两者都是方向层的输入。而它们自己的落盘（`.intent/`）**独立于两者**，且在**仓库内**（跟代码一起进版本库）—— 它是**原料**，不是配置。

### 交界：方向层交什么，流动层接什么

| 方向层出 | 流动层接 |
|---|---|
| 需求变更（新建 / 换范围 / 作废，都落成票 + 原因） | 票进「迷雾」或「发现」；**要插队，先停一张在制品** |
| D1 一张排好序的候选清单（三个动作） | 取票顺序按它；流动层**不重排**优先级 |
| D2 里程碑的完成定义 | 里程碑没过 → **该里程碑下的票冻结**，整块看板照常流动 |
| D4 给票打「待批准」标记 | 带标记的票**不进「取票池」、不占 N**；标记摘掉才进「待开工」 |
| 闸 T 声明的单票阻塞边 | 汇总进**全局依赖表**（落盘 `direction.md`），D1 读它判断"被阻塞的不进候选" |

**冲突时听谁的**：**你拍了板就按你的** —— 下面所有规则都只是没人拍板时的默认序。

## 方向层

**落盘**：`docs/agents/direction.md` —— 优先级清单、里程碑、全局依赖表、待批准登记。

**盘点结果和原话库不在这里**：它们落在**仓库内的 `.intent/`**（原料，跟代码一起进版本库），本层只放指针。**这两样不是方向层的配置，是方向的依据。**

**决策账本不在这里**：只认 `docs/agents/flow.md` 指明的那一份，本层放指针。

### 盘点：先盘一次，再调度

**接手一个项目，第一件事是搞清楚「这项目有哪些功能、做到哪一步了」**，然后才排期。它是方向层的入口动作，跑在 `/wayfinder` 之前。

**这是一道入口闸门，不是一个可选项。** 没盘过、或上次盘点已过期 → **不许往下走任何一步**（闸门条件与重跑时机见上面「入口」）。直接开票排期，等于在没有功能全表的情况下赌「需求不会漏」；漏掉的那部分没人能发现，因为**没有东西可以拿来对照**。

三条理由：决策账本记的是**决策**不是**功能枚举**，两者不能互替 · 没有功能全表，「需求太多」会直接压进「迷雾」列，而**没人能判断决策是否覆盖了全部功能** · 盘点会**推翻过期的自述**，而这些自述正被下游票引用。

**三步走**

1. **切块** —— 按项目自身的天然边界切（代码 / 知识 / 文档 / 质量 / 待吸收），每块一个盘点单元
2. **逐块扫** —— 每块产出一行一条的清单。**一条 = 一个功能**
3. **收口** —— 合并成一份入口总表，数出三个数字

**盘点算完的判据（三条全中才算完）**：① 每一块都有清单文件落盘 · ② 入口总表的数字与分块**逐条数出来的**数字对得上 · ③ 与旧自述冲突之处全部写进了 `.intent/drift.md`。少一条，这步没完。

**产出三件（缺一不可）**

| # | 产出 | 内容 |
|---|---|---|
| 1 | **功能全清单** | 每一个**已有**功能一条：功能名 — 一句话人话说明 · 位置（写到文件） · 状态 |
| 2 | **需求侧清单** | 还没做但要做的事（待吸收 / 待决策），一条一行 |
| 3 | **入口总表** | 规模数字 + **进度数字** + 按业务主线分组。入口那几栏（要你拍板 / 能开工 / 还轮不到）按 D3 的分组口径写 |

**落盘**：`.intent/inventory/` —— **仓库内，跟代码一起进版本库**（不是仓库外）。入口总表、功能全清单、分块明细都放这里，**每次盘点用同一处，别换**。骨架见 [`templates/inventory.md`](templates/inventory.md)。

#### 盘点纪律

- **逐条数** —— 状态计数逐条数出来，不是估的；估出来的数字会污染进度读数
- **状态只有三个值**：`已有` / `做了一半` / `还没做`。同一条东西**只在一处计数**
- **「已有」的判据**：能跑通 + 有人写下怎么用 + 有测试或验收入口。**三条缺一，状态降一级**
- **一条功能一行，位置写到文件** —— 方便回头验证
- **需求侧每条标身份**：走「迷雾」还是直接成票，以及谁负责推进它
- **和前文冲突时以实测为准，并回写** —— 盘点的副产物天然是 `.intent/drift.md` 的条目
- **盘全部产出** —— 代码只是其中一块（实测某项目 573 条功能里 282 条不是代码）
- **只盘可交付的功能** —— 临时脚本、废弃实验、一次性数据处理都不算
- **重跑时机**：每个里程碑过闸时 + 每周复盘时

### 收原话与译：对方要什么

**另一个入口。** 盘点盘的是**手上有什么**，这一站收的是**对方要什么**（入口对照表见上面「入口」）。

**它为什么单独成一步**：需求方**不懂软件**，需求**总在改**，原料**只有聊天记录或一份乱文档**。这三条同时成立时，「模糊进迷雾、改动走变更」接不住 —— 那套假设**需求已经有人收到了**，而这里的问题是**还没有地方把他说过的话存下来对账**。

**第一性原理一条：原话是唯一真相源。** 一切写在 markdown 里、在 git 里、可被下一个 agent 读到。**「需求总是不明确」的机械原因不是他没说清，是没有原话账本可以拿来对账。**

**落盘**：`.intent/raw/` + `.intent/GLOSSARY.md`（**完整布局见上面「入口」的树**，那里是唯一真相源）。

**共同动作（每一轮、每种原料都做）**：

1. **原文只读** —— 原文整份原样落 `raw/_src/`，**一个字不改、不删、不整理**
2. **逐条标可信度** —— 派生件一条一块，**每条都带出处**（文件名 + 行号，或时间戳 + 发送人）
3. **收口数数** —— 逐条数出数字，并**落盘抽检核验表**（**填不满 5 条 = 这一站没完**）

**按原料选路（一次只走一条）** —— 派生件命名按 `NN` 段位，**只看「哪来的」，不看「怎么收的」**：

| 段位 | 原料 | 读哪 |
|---|---|---|
| `10` | **文档**（原始材料 / **半成品稿** / 需求备忘） | [`DOC-INTAKE.md`](DOC-INTAKE.md) —— 半成品稿乱的是**可信度**，不是结构 |
| `20` | **聊天记录**（微信 / 飞书 / 邮件） | [`CHAT-INTAKE.md`](CHAT-INTAKE.md) —— 五种真需求句式 |
| `30` | **面谈**（当面说的、这轮对话说的） | **没有文件** —— 立刻落 `30-interview-<日期>.md`，用他的原词 |

**收完就换 context** —— 交回后由**下一个 context** 起 ② 判（`/handoff`）。原料里全是闲聊和口语，会对译的推理产生噪声（边界理由见 [`FLOW-REFERENCE.md`](FLOW-REFERENCE.md)「阶段边界」）。

**收算完的判据** —— 见各原料的文件。**三条共通底线**：① 每份原料都有落盘文件，**每一段都带得出处**，且**抽检核验表已落盘**（5 条实查全对）· ② 与旧自述冲突之处**全部**写进 `drift.md` · ③ **逐条数出来的数字**（不是估的），数哪几个各原料不同。

**纪律**：原文**逐字照抄**（他写「要能看出来谁做得好」，就照抄这一句；润色过的原话三个月后没人能验证它是不是原意）· **一句原话可以喂三条需求**，不要求一对一 · **收的时候只记录** —— 追问归 ②。

#### ② 判：需求方只做三类判断

**所有提问必须能落进这三类之一，落不进的就是不该问的问题。**

| 类型 | 长什么样 | 谁答 |
|---|---|---|
| **判断题** | 「这个草案，改哪儿？」「这两个顺序，哪个先？」 | **需求方** |
| **确认题** | 「你的意思是 X，对吧？」 | agent 复述，需求方点头 |
| **事实题** | 「照片能不能拍清楚？」「这套量表有没有版权？」 | **不是需求方的活** → `/research` 或 `/to-questionnaire` |

**核心操作：不问开放题，出草案让他改。** 开放题答不出来是**必然的** —— 答案要求他已经知道可能的答案有哪些。一份写着「我猜是这样，改哪儿？」的草案，胜过二十个开放问题。

**闸 R（过滤）**：每条要问的东西先过一遍 —— **它影响「做什么」吗？** 不影响 → 丢掉 · 影响 → **我能用一份草案把它变成判断题吗？** 能 → 出草案 · 不能 → 分性质：**人**（只有他能定）进迷雾 · **事实**走 `/research` · **产物**排进 backlog，**不问他**。

**跟不懂软件的人怎么问** —— 禁用题型、四个改问法、术语禁用表、**「你决定吧」出现时怎么办** —— 读 [`PROBING.md`](PROBING.md)。**核心是「弃权即未定」**：对方沉默、用错术语或讲别的，说明草案不够具体；弃权时做的决定等于需求未定就开工。

**判算完的判据（三条全中才算完）**：① **这一轮收进来的每一条原话都有去向** —— 出草案 / 进迷雾（写明「谁的问题 + 不知道什么」）/ 走事实题 / 明确丢掉；没有一条停在「先放着」· ② **推给需求方的那一批 ≤ 5 条，且至少 4 条是判断题** · ③ **每一个「待定」都写清了要问谁**（需求方本人，还是别人 → `/to-questionnaire`）。

#### ③ 译：产品语言，但留一根线回到原话

**一条需求条目的形状**（骨架在 [`templates/requirements.md`](templates/requirements.md)）：

```
R12 · <一句人话>
原话：raw/20-chat-wechat-0912.md C-014「要是能直接看出来谁做得好就好了」
翻译：<产品语言，含数据字段 / 交互 / 边界>
占位符（agent 能填的）：<技术选型、字段名>
待定（只有需求方能填的）：<他才知道的业务事实>
状态：草稿（第 1 次）
```

**五条硬规矩**

1. **一条需求一条原话。** 追不到原话的需求 = **凭空发明**，删掉
2. **标出「占位符」和「待定」** —— 不写出来，agent 就会替需求方编业务事实
3. **需求方不直接编辑文件** —— 他说的改动由 agent 落笔，并记下改了第几次
4. **改动不改写历史** —— 新增版本，旧版本保留
5. **一次只推一批，不超过 5 条** —— 50 条一起给，他只会说「都行」

**译算完的判据（三条全中才算完）**：① **每一条需求都追得到原话**（抽 5 条点回 `_src/`，5 条全对）· ② **每条都填了「占位符」和「待定」两栏** —— 空着就写「无」，不许留白 · ③ **条目编号唯一且接得上前一版**（改动走新版本，旧版本还在）。

**这批推完 → 条目过「三道闸门」里的闸 S 和闸 T（那是 ④ 放行），然后按「需求管理」往下流。**

### 需求管理：模糊进迷雾，改动走变更

需求**模糊**和需求**常改**是两条不同的路。走错一条，在制品就被搅乱了。

**模糊 → 进「迷雾」，不在实现里猜**

- 一个问题还没成形 → 进「迷雾」，用 `/grilling` 问清楚
- 一个 session 装得下 → `/grill-with-docs`；装不下 → `/wayfinder` 出决策票
- **出口判据：写得出「这是谁的问题 + 现在不知道的是什么」** —— 写得出就收敛成一张决策票，进「发现」。**只写得出"做个 XX"的不是迷雾，是这一轮就该排的票**
- **主动放弃也算出口**：判断不值得追了，就在决策账本记一句「已知，决定不再追」，并把它移出「迷雾」—— 挂在里面的东西没人再看
- 「迷雾」和「发现」是**常驻车道**：需求会持续不清晰，不是一次性能问完的

**改动 → 走变更五条，只换范围、不动在制品**

| # | 规则 |
|---|---|
| 1 | **改动落成票** —— 新建一张，或更新原票；它进「迷雾」或「发现」。已经在「进行中」的票要改，就重走闸 T |
| 2 | **只换范围** —— 范围可以砍，**在制品不动**。N 是硬的：要插队，先**停一张** |
| 3 | **记下改动和原因** —— 写进决策账本（只增不删）。三个月后"当时为什么改"只有这里回答得了 |
| 4 | **改动过闸** —— 影响 spec 的走**闸 S**，影响票粒度的走**闸 T**；动到里程碑完成定义的，重走 D2 |
| 5 | **作废也走变更** —— 需求被取代或放弃时：先停掉它的 agent（若在「进行中」），票移出看板并标 `wontfix`，**写明被哪张取代或为什么不做**，记进决策账本。作废**不占 N** |

**「只换范围」说的就是这一句**：**范围变不是问题，在制品变才是。** 做不完就砍范围 —— 砍范围靠 D1 重排 + D4 审批，不靠在「进行中」加塞。

### D1 优先级：先做哪个

**一次推三个，在每个批次开始前推一次。产出是三个动作，不是一张排序表。**

**候选池** = 「待开工」里没被阻塞的票 + 本轮刚从「迷雾」收敛出决策的票 + 止损类动作。**不进候选池的三类**：带「待批准」标记的 · 被阻塞的（除非阻塞源本身就在这一轮）· 冻结里程碑下的。

按顺序判断，**前面的一条压过后面的**：

1. **止损动作优先** —— 推送备份、把没备份的东西备份掉、锁住正在丢的东西。成本≈0，收益是消除单点丢失。**这类动作也进候选池**，它们常常"不是功能"。**（下称「止损动作」；待验收越期时，汇报只出这一类）**
2. **解锁收益最大** —— 解开一个卡点能让后面好几张票同时解锁的
3. 剩下按这一句排：**"力气小、做完能放开后面几件，就先做它"**

**重排时机**：每个批次开始前 + 每周复盘时。

> 例子：某张票花 3 小时、做完能放开后面 5 张 → 排第 1；另一张要 3 天、只放开自己 → 排后面。

### D2 里程碑

**颗粒度：一条业务主线一个** —— 按批次开会生出 54 个里程碑，等于没有。

**完成定义必须写全三样，缺一就当没定义**：

1. **跑什么命令**（项目里真能跑的那条，例如 `npm run verify` 或 `pytest`）
2. **通过门槛**（测试全绿？还是某几项硬指标全过？）
3. **最晚日期**

写不出这三样，它不是里程碑，是愿望。**写不出就如实记「里程碑待定」**，并把「造出第一条能跑的命令」排到候选清单第一位 —— **硬写一个假里程碑比不写更坏**。

- **gate 在一条业务主线内串行** —— 同一主线上，上一个没过，不开下一个；**不同主线的里程碑并行**，这是「一条主线一个」的必然结果
- **判定** = 该里程碑的完成定义 + 闸 V 结论
- **没过时冻结**：冻结**该里程碑下的票**（这条主线停），**其他主线照常流动**
- **对账**：每周回顾第 1 问必须回答「里程碑 vs 实际」
- **验收资产用现成的** —— 项目里已有的就用它（例如五项硬指标、65 条人工标准答案）。新造一套等于凭空多一份要维护的东西

### D3 汇报

**格式只在这里定义一次** —— 盘点的入口总表也用它。

**按「这事归谁做」分组**：读者一眼看懂该干什么；按状态列横排的表格读者看不懂。

```
【一行数字】进行中 x/N · 待验收 y（最老 z 天）· 待批准 w（最老 v 天）· 里程碑 第 k 个 / 共 m 个 · 下个里程碑预计 <日期区间>

【要你拍板的】...
【能马上开工的】...
【还轮不到的】...

【卡在哪】一句话
```

**取数来源**

| 要什么 | 从哪取 |
|---|---|
| 进行中 / 待验收 / 最老年龄 | `flow-metrics.mjs` + 票状态 |
| 待批准 | 按 `docs/agents/issue-tracker.md` 里本仓库的取票命令查 |
| 预计完成日 | `flow-metrics.mjs` 的周期时间 × 剩余票数 ÷ N |
| 里程碑 | `docs/agents/direction.md` |

**四条硬规矩**

1. **每次重新生成** —— 手写快照会过期
2. **用大白话** —— 把吞吐 / 收敛 / WIP 换成日常词
3. **入口和明细分家** —— 入口只给数字和结论，明细指向文件
4. **数字打架时以决策账本为准**，并回写修正

**警报期内的例外**：待验收超过阈值时，这份汇报**只出止损动作**（定义见 D1 第 1 条）。

### D4 审批

**「待批准」不是第七列**，是票上的一个标记 —— 带原生 label 的 tracker 上是 `ready-for-human` 标签；本地 markdown 票面上就是 `Status: ready-for-human`。**具体形式归 `docs/agents/issue-tracker.md`。**

| 问题 | 答案 |
|---|---|
| **批准人** | 票的 description 里固定一行 **`批准人：<名字>`** —— 没有名字的批准等于没有批准 |
| **占不占 N** | 不占。带标记的票**不进「取票池」**、不算并行位 |
| **未批准** | 不开工，也不往上堆 |
| **已经干完了** | 如实记成已经投入的工时 |
| **升级** | 挂满 **3 天** → 升到下次汇报的头一条并单独念出来 |
| **汇报** | 「待批准」**单独一栏**，永不并在「进行中」里 |
| **批准之后** | 直接进「待开工」，不重排优先级 |
| **答案不在会上** | 需要别人（不是拍板人）回答才动得了 → `/to-questionnaire` 出问卷 |

**批准 ≠ 闸 T**：批准是"这件事要不要做"，闸 T 是"这张票拆得对不对"。**两道都要过。**

## 流动层

### 在制品上限（WIP）

整个框架只有一个数字 —— **在制品上限**：

```
并行 agent 数 N  ≤  你每天能真实验收的 PR 数
```

- **限流点在「进行中」** —— 它决定你向「待验收」注入的速率
- **「待验收」是仪表，不是限流点**：它上不封顶，而它的深度和最老年龄**校准 N**
- **警报**：待验收最老一张超过阈值（默认 2 天）→ **停手，只做验收**

N 是个写下来的数，不是感觉，住在 `docs/agents/flow.md`。**「进行中」只算你自己起的 agent**，并发会话里别人在同一个仓库里跑的不算。

**为什么这一个数字比其余所有仪式加起来都重要**：N 个 agent 各自"局部最优"地改代码，合起来是全局腐烂 —— 限制 N 就是不让代码库被同时从 N 个方向撕开。

> 按量计费的项目再加一条上限：token 预算撑得住的批数。包月不限量就只有验收吞吐这一条。

### 看板：六列

| # | 列 | 票在这里意味着 | 离开条件 |
|---|---|---|---|
| 0 | **迷雾** `fog` | 一个问题，还没成形 | 写得出「谁的问题 + 不知道什么」→ 收敛成决策票，或明确放弃 |
| 1 | **发现** `discovery` | 决策票：答案是决策，不是代码 | 决策定了 → 并入下游 |
| 2 | **待开工** `ready` | 有验收标准 + 已声明阻塞边的 tracer bullet | 闸 T 已过 → agent 拉走 |
| 3 | **进行中** `building` | N 个 agent，一票一 agent，一票一 fresh context | `/implement` 提交 |
| 4 | **待验收** `verifying` | agent 干完了，**没有人判断过** | 闸 V 裁决 |
| 5 | **已完成** `done` | 验收通过 | 人裁决通过（记**判定人 + 日期**） |

**迷雾和发现是常驻车道**：需求持续不清晰，不是一次性能问完的。**票不跳列** —— 六列的离开条件见「看板」。

**状态变更单独提交一次** —— 否则周期时间算不出来，它来自 `git log` 里的状态转移。

### 三道闸门

闸门是**阻断式**的：票不能越列。对话式确认（"check with the user"）不叫闸门。

| 闸 | 位置 | 通过标准 |
|---|---|---|
| **闸 S**（Spec） | `/to-spec` 之后、`/to-tickets` 之前 | 你读过 spec，确认**测试缝隙（seams）**符合预期 |
| **闸 T**（Tickets） | `/to-tickets` 之后、进「待开工」之前 | 确认粒度、阻塞边，以及**验收标准已经写成人能照着跑的东西**（哪条命令、什么门槛、期望输出） |
| **闸 V**（Verify） | `/implement` 提交之后 | 裁决 `/code-review` 结论，**并对着真实重跑一遍验收标准**；只有一项不达标 → **把那项转成新票退回**，不整张打回重做 |

**闸 S 和闸 T 由人把守，且串行** —— 这两道决定"做对的事"。让 agent 自动通过，你就把方向控制权交出去了，而那是需求混乱的入口。

**需求方看不懂 spec 时**（他不懂软件，这是常态）：**把闸 S 换成他看得懂的东西** —— 用 `/prototype` 出原型，**让他在原型上点头**。**原型就是需求方的 spec**，闸的标准不变（人对「要做成什么样」拍了板），只是换了载体。

从 `/wayfinder` 出来**并入 `/to-spec`**（也就是过闸 S），不直接进 `/implement` —— 直接进会跳过"把地图的关联决策坍缩成计划"这一步。

复核分两层：`/implement` 提交前先跑 agent 自审（`/code-review`），票进「待验收」后**你**裁决那个结论。

### 全局依赖表（谁挡谁）

闸 T 只声明**一张票**的阻塞边。全局表把它们汇总起来，一眼看出**卡在哪、卡住了多少东西**。

**一条 = 一行**：`阻塞源 → 挡住的票（几张）· 性质 · 解除条件 · 卡了多久`

| 性质 | 什么意思 | 解除动作 |
|---|---|---|
| **人** | 等你拍板 / 等你批准 | 排进下一次汇报的「要你拍板的」 |
| **事实** | 有个东西必须先测出来、必须先定清 | 开一张票去做它 |
| **产物** | 前一个东西必须先做出来 | 等它过闸 V |

1. 每个批次开始前更新一次 —— 闸 T 那一刻声明完不等于更新完
2. 阻塞源解除当天，把它挡住的东西放出来
3. **「卡了多久」必须记** —— 卡了三周和昨天刚卡的，不是一回事
4. 这张表**只回答"谁挡谁、卡了多久"**，排序是 D1 的事

> 例子：`黄砖语义未定 → 挡住 2 张（F2 探测器、F3 过滤器）· 性质：人 · 解除条件：你裁定黄砖含义 · 卡了 __ 天`

### 节奏

| 事件 | 触发 | 频率 |
|---|---|---|
| **补充（pull）** | 「待开工」少于阈值（默认 3）时，从「发现」拉新票 | 触发式，非迭代 |
| **每日** | 只看一个数：**待验收最老一张的年龄** | 每天，5 分钟 |
| **回顾** | 固定时间 | 每周，30 分钟，**硬日程** |

**回顾四问**：① 完成 vs 计划的偏差，**并回答里程碑 vs 实际** ② 这周定了哪些决策 → **回写**决策账本 ③ 技术债：跑 `/improve-codebase-architecture` 出候选 ④ 下一个待决问题。

**为什么回顾必须是硬日程**：这一层是减法框架 —— 假设你已有工程纪律，然后去掉束缚。从零开始的团队直接上，回顾是第一件消失的事，整套随即退化成"一个没有流程的看板"。**三样必须手动补：固定回顾、固定补充触发、完成定义。**

### 度量

框架的另一半是**读数**，没有它「待验收在堆高」只是感觉。

`flow-metrics.mjs`（`setup-cadence` 交付，路径由 `docs/agents/flow.md` 指定）给五个读数 —— 算法与字段名见脚本 `--help` / `--json`，这里只写**每个读数用来干什么**：

| 读数 | 用途 |
|---|---|
| 「待验收」最老一张的年龄 | 每日那一眼；超过阈值就停手 |
| 周期时间（ready → done） | 校准 N 的依据 |
| 「待验收」积压的**周趋势** | **比当前值更重要：它涨，说明 N 填大了** |
| **返工次数**（退回重做） | **返工变多时，停的是新开工** |
| 预计完成日 = 周期时间 × 剩余票数 ÷ N | 回答"什么时候算完"；**给区间** —— 中位与 p85 各算一次，不给单点 |

读数来自 `git log`。**退回重做的票，周期时间从重新进「进行中」起算。**

**票面状态承载两套语义** —— 六列 + triage role（见 `docs/agents/triage-labels.md`），脚本按**最近的一列**归类（`ready-for-human` 落进「发现」）。所以「待批准」的年龄要去 tracker 查，别从看板读。
