# 文档原料入库

[`SKILL.md`](SKILL.md) 的 收原话 · ① 收 推下来的参考。**只在原料是一份文档（或几份）时读。**

**最常见的原料是「半成品稿」** —— 已经有人（上一个 agent、你自己、同事）整理过一遍的东西。它**结构往往是好的**（标题准确、有总表、有目录），**乱的是别的东西**。搞错乱在哪，这一站就白做。

---

## 铁律：原文只读，派生件带出处

**原文档整份放 `.intent/raw/_src/`，一个字都不许改、不许删、不许整理。**

**派生件写在 `.intent/raw/10-doc-<文件名>.md`，每条指回原文行号。**

**为什么**：三个月后两个人对同一段的读法分岔时，**唯一能仲裁的是原文那几行**。原文被整理过，仲裁就没用了 —— 而且整理过的东西**看起来更权威**，于是没人会回头怀疑它。

---

## 先判断：这份文档是什么

**三种形态，做法完全不同。**

| 形态 | 长什么样 | 乱在哪 |
|---|---|---|
| **原始材料** | 会议记录、政策文件、别人的稿子、聊天导出 | **结构** —— 标题不反映内容，话题散落多处 |
| **半成品稿** | 有人已经整理过一遍：有总表、有目录、**带自己的记号** | **可信度** —— 结构是好的，但分不清哪句有出处、哪句是推的 |
| **需求备忘** | 对方自己写的「我要什么」清单 | **常常没有** —— 这类最少见，也最不需要这个文件 |

**判据**：**看文档有没有「状态行」和「来源行」。** 有 → 半成品稿。

> 例：一份文档开头写「**状态**：草稿 —— 玩法栏来自公开报道原文，但「推荐人数 / 时长 / 可调难度 / 适用人群与禁忌」四栏基本都是我推的」。
> **这一句就是整份文档的使用说明书。** 它告诉了你乱在哪。

---

## 铁律二：沿用文档自带的记号，不要另发明一套

**半成品稿几乎都带自己的记号体系。** 常见的有：

| 记号 | 意思 |
|---|---|
| `【推】` | **作者推断的**，原文里没有这一层 |
| `⚠️` | 作者自己标出的**不确定 / 缺口 / 风险** |
| `主` / `次` | 靶向 vs 顺带涉及 |
| `报道未给规则` | 原始来源里查不到，作者拒绝编 |
| 「**等你改**」/「**待拍板**」 | 作者自己提的问题 |

**你的活是继承这套记号，不是替换它。**

- **派生件里照抄这些记号** —— 收了 124 处 `【推】`，就标 124 处
- **要加记号就往上加，别改名** —— 文档说 `【推】`，你的派生件也说 `【推】`；创建 `[推断]` 这种同义词，等于让下一个读的人做一次翻译
- **作者的记号本身就是最贵的产出** —— 他标了 `【推】`，说明他知道自己哪里没底。**你的工作是把这些集中起来，不是重新判断一遍**

**为什么**：另发明一套，两套记号就会各自漂移，而且**作者原来标的那些会被读的人忽略**。

## 先找文档自己给出的索引

**别急着从头读。半成品稿通常自带四样东西，先找它们：**

| 先找 | 在哪 | 它替掉了什么 |
|---|---|---|
| **总表 / 附表** | 开头的表格 | **一张 30 行的总表，比你自己扫 700 行强得多** |
| **问题清单** | 附录里的「等你改」「待拍板」 | 作者已经识别的待决项，**最高优先级的需求来源** |
| **来源清单** | 文末「按域名 / 按机构」 | 出处的核对底本 |
| **字段说明** | 开头的「字段说明」表 | 这份文档自己的字段定义 |

**这四样是文档作者替你做的活。** 找到了就从它们反推结构，**找不到才逐段读**。

**超大文档两遍法**（总表也没有时用）：

1. **第一遍只读标题 + 每段第一句**，不细读 → 出一张块索引
2. **第二遍按块索引逐块读** → 派生件

整份进 context 的后果不是变慢，是**后面的推理被前面的噪音污染**。

## 分的是「可信度」，不是「类型」

**这是与直觉相反的一点**：文档里的段落，**不是按「需求 / 事实 / 政策」分类**，而是**按「这句话有多可信」分层**。

**逐条标这一栏**（下面六个值，**只选一个**）：

| 值 | 什么算 | 怎么处理 |
|---|---|---|
| **有出处** | 能点回去自证 —— URL、条款号、页码 | 记下出处，**不用问对方** |
| **`【推】`** | 作者推断的，**原文没有这一层** | **这是最需要对方改的一类。** 集中起来送 ② 判 |
| **`⚠️ 缺口`** | 作者标出「这里填不进去 / 查不到 / 我不确定」 | 送 ② 判 → 多半是**决策**（要人拍板）或**事实**（要查证） |
| **文档自提的问题** | 附录里的「等你改」 | **直接进 ② 判**，它已经成形了 |
| **已定** | 写着「已定」「不再讨论」 | 进决策账本，**不进需求清单** |
| **噪音** | 重复、过时、跟本项目无关 | 登记一句，标无关 |

**为什么「有出处」和「`【推】`」要分开**：这两类**混在一起时长得一模一样** —— 都是陈述句，都言之凿凿。而**它们的处理方式相反**：有出处的不用管，`【推】` 的每一条都要对方过目。混着读，你会把作者推的东西当成事实用下去。

> **「依据」不需要单独一类。** 政策的条款号、公开报道的 URL、教科书的页码 —— **都只是「出处」的不同形态**，归在「有出处」里记下它是什么就行。**单独设一类会让你去猜该归哪类，而它们本来就一样。**

## 需求往往不写在文档里

**半成品稿里几乎没有一句写着「这是个需求」。** 需求要从四个地方**推出来**：

| 从哪推 | 例子 |
|---|---|
| **用途声明** | 「**你明天下午就能照着带**」→ 需求：能照着带 → 步骤必须完整 |
| **缺口** | 「⚠️ 手指精细 —— 词表无家」→ 需求：词表补这一类 |
| **`【推】` 栏** | 「适用人群 / 禁忌 —— 请务必自己再过一遍」→ 需求：对方要核定这一栏 |
| **自提问题** | 附录「**分类对不对？**」→ 需求：对方要回答，答案改变数据结构 |

**这四类恰好就是最高价值的需求** —— 因为它们**带着证据**（作者已经写清了为什么缺、缺在哪一行），比对方口头说一句「这里不太对」精确得多。

**反过来**：真正的需求**很少**在「这是需求」这类标题底下 —— 那类标题下通常放的是作者已经做完的事。

## 乱法有三种，分别怎么处理

| 乱法 | 症状 | 处理 |
|---|---|---|
| **结构乱**（原始材料） | 标题不反映内容、同一话题散落多处、目录正文对不上 | 按语义转场切；**以内容为准，冲突处进 `drift.md`** |
| **可信度乱**（半成品稿） | 结构很好，但**分不清哪句有出处** | **逐条标可信度**（上表）+ **沿用它自带的记号**；不重切结构 |
| **版本乱** | 同一份东西有 v1 / v2，说法不一样 | 都收，**标版本和日期**；差异进 `drift.md`。**别只收最新版** —— 旧版里常有新版丢掉的原始说法 |

**结构乱时才有「标题会骗人」这回事**（标题写 A 内容是 B、目录正文不符、同一话题散落多处）。**半成品稿的标题通常是准的，别把它当骗子查。**

## 切分单元：跟着文档的天然单元走

**不要发明切法。** 半成品稿通常已经切好了：

| 文档 | 天然单元 |
|---|---|
| 一份活动合集 | **一个活动**（一个 `###` 节 + 它在总表里的一行） |
| 一份病种科普 | **一个病种** / **一个话题** |
| 一份带缺口分析的稿子 | **一个缺口** |

**派生的每条 = 一个天然单元**，而不是「一段」。

**判据**：**把这一条单独拿出来给一个陌生人看，他能不能看懂在说什么？** 看不懂就是切错了。

**同一单元里的不同可信度要拆开标** —— 一条活动的「玩法」可能是有出处，「禁忌」是 `【推】`。**拆开，不要因为它们在同一个标题下就合并。**

## 派生件格式

模板见 [`templates/raw-doc.md`](templates/raw-doc.md)。骨架：

```markdown
## D-014 · <天然单元名>
**原文**：「……」（照抄，**含错别字，不润色**）
**出处**：`_src/<文件名>` L1204–1208
**可信度**：有出处 / 【推】/ ⚠️ 缺口 / 文档自提问题 / 已定 / 噪音
**如果有出处**：<URL / 条款号 / 页码 —— 照抄成能点回去的样子>
**文档自带的记号**：<照抄原文用的记号，如 【推】>
**我的理解**：<产品语言初译，允许不准>
**关联**：D-009（同一件事，2.1 节说了一半）、C-021（聊天里也提过）
**状态**：未译
```

**编号 `D-NNN`，全局唯一。** ③ 译 的 `R-NN` 引这个编号 —— **这是原文到产品之间那根线。**

**「关联」栏必须在收的时候填。** 同一话题散落多处时，往往只有一处写清楚了，另两处是残句。**收的时候不标，③ 译 的时候就得重读全篇。**

## 收口判据

**三条全中，一份文档才算收完**：

1. **每一块都有出处**（`_src/` 文件名 + 行范围）—— **硬性对账**：派生文件末尾必须保留「抽检核验表」，由 agent 实查填入 5 块出处的行号与原文前 20 字，5 条全部吻合
2. **`【推】` 和 `⚠️` 一条不漏地集中起来了**，且**文档自提的问题全部进 ② 判** —— 这三样是这份文档最值钱的部分
3. **数出四个数字**：块数 · 有出处条数 · **`【推】` 条数** · 与旧自述冲突的处数（后者进 `drift.md`）

**第 1 条的抽检核验表格式（派生件末尾必填交付物）**：

| 抽检ID | 原文行号 | 原文前20字摘录 | 核验状态 |
|---|---|---|---|
| D-003 | L45–48 | 「...」 | ✅ 一致 |
| D-014 | L634 | 「...」 | ✅ 一致 |
| D-022 | L912–915 | 「...」 | ✅ 一致 |
| D-031 | L1102 | 「...」 | ✅ 一致 |
| D-045 | L1520 | 「...」 | ✅ 一致 |

（少于 5 条或未落盘核验表，本阶段视为未完工，不准推进至 ② 判）

**第 2 条是这一站的核心。** 一份文档的价值不在于它写了多少，在于**它标出了自己哪里没底** —— 漏掉那些标记，你就把一份半成品当成了成品用。

## 一段示例（虚构，只看格式）

```markdown
## D-014 · 蒙眼敲锣
**原文**：「报道原文写获胜者『凭借出色的方向感和稳定的步伐，成功敲响了铜锣』」
**出处**：`_src/游戏合集.md` L634
**可信度**：有出处
**如果有出处**：`jshasy.com`（淮安市第三人民医院活动报道，见 L676 来源清单）
**文档自带的记号**：无（正文陈述）
**我的理解**：这是 §6.1 用来证明 `b114 定向功能` 被漏收的**证据活动** ——
              **它不是需求，是证据。** 它支撑的需求在 D-020（补回 b114）
**关联**：D-020（词表缺口）、L71 总表里这一行标着「⚠️ 词表无家」
**状态**：未译
```

```markdown
## D-015 · 蒙眼敲锣的禁忌栏
**原文**：「有吞食异物风险的患者（如痴呆、精神…」（被截断）
**出处**：`_src/游戏合集.md` L273
**可信度**：`【推】`
**文档自带的记号**：`【推】` + 文档原话「**这是安全栏，请按你科室的实际评估口径覆盖**」
**我的理解**：**安全相关，必须由对方核定。** 送去 ② 判 —— 这是判断题，不是问答题
**关联**：D-014（同一个活动）
**状态**：未译
```

> 注意这两条的差别：**D-014 有出处，D-015 是推的**，而它们在原文里**隔着 300 多行、在不同章节**（一个在 §5 活动正文，一个在活动自身的禁忌栏）。
> **收的时候必须把它们串起来** —— 否则 ③ 译 会得到「禁忌栏已填好」的假象，而那一栏**根本没被任何人确认过**。
